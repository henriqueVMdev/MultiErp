# AGENTS.md

Instructions for AI coding agents working in this repository. Keep this file short and current. If it contradicts the code or the maintainer's latest instruction, ask the maintainer instead of guessing.

## 1. Project

Working name: `erp-connector-lib` (placeholder, final name TBD).

A Java library that connects to third-party ERP systems, reads sales data (orders) and returns it in a single canonical model, so applications that use the library never deal with each ERP's own format. Adding support for a new ERP means writing a connector. Nothing else changes.

Status: in development. Canonical model, connector interface, errors and retry implemented; `testkit` next.

The library is **stateless** and **framework-free**. It does not persist anything. Whoever uses it stores sync cursors, credentials and tokens, and decides when to run.

### Modules (Maven, all three from the start)
- `core`: canonical model, connector interface, typed errors, validation utilities (for example CPF/CNPJ check digits).
- `testkit`: the conformance suite every connector must pass. Published separately so third-party connector authors can reuse it.
- `connector-<erp>`: one module per ERP.

Connectors for private or in-house systems are not part of this repository. They live in their owners' repositories, depend on `core`, and prove conformance by extending the `testkit` suite.

### Out of scope for this repository
Web service, UI, database or any persistence, analytics or insights, data enrichment, multi-tenancy, webhook receiver, Spring Boot starter. These belong to applications that consume the library, not to the library. If a task pulls toward any of them, stop and ask the maintainer.

## 2. How to work with the maintainer

Default mode: **you write the code, the maintainer reviews.**

- **Tutor mode when asked** is opt-in, per section ("tutor mode for this part"). Only then, do not generate code: explain, ask questions and check the maintainer's reasoning. Otherwise implement.
- **Ask before deciding** anything that becomes public API or is expensive to change: the canonical model, the connector interface, error types, retry policy, sync semantics, module boundaries. Do not decide alone and report afterwards.
- Decide yourself on small, reversible things: local names, internal package layout, test utilities.
- Before any step that touches architecture, post a short plan (10 lines max) and wait for confirmation.
- **The maintainer makes the commits.** Do not commit or push. At the end of each step, hand over the exact git commands: small commits, one concern each, messages in English, imperative mood. Tests green before saying a step is done.
- New dependency: one-line justification first. Keep `core` as lean as possible.
- When you finish a step, report what you did, what you decided on your own, and what is pending for the maintainer.
- Do not state facts about an ERP's API from memory. Read its current official documentation. Mark anything you could not verify as "unverified".

## 3. Hard rules

1. **Public from the first commit.** No secrets, no real customer data, no real payloads in the repository, tests, fixtures, logs or docs. Fixtures are synthetic. Fake CPF/CNPJ values in tests are generated by the check-digit algorithm, never real numbers. Credentials come only from environment variables or a configuration object supplied by the library user. `.env` is git-ignored.
2. **The library does not know its users.** No names, hostnames, account ids or business rules of any application that consumes it, anywhere in code, tests, fixtures or docs. `core` does not depend on any connector, Spring, or Jackson.
3. **No global state.** No singletons, mutable statics or global caches. One connector instance per ERP account, so several accounts can run side by side without mixing.
4. **Personal data.**
   - CPF/CNPJ, e-mail and phone never appear in full in logs, exception messages or `toString()`. Mask them.
   - Tokens, refresh tokens and secrets never appear in logs.
   - The library **reports** data. It does not decide whether a given use of that data is allowed. That is the consumer's responsibility.
5. **Never invent data.** A field the ERP does not provide stays unknown, never an assumed value. In particular, if the ERP does not say which sales channel an order came from, the channel is `UNKNOWN`, never `DIRECT`.
6. **Bad data does not abort a load.** An invalid CPF, a total that does not add up, an unknown status: the record is returned with an anomaly attached. Exceptions are for communication failures or formats that make the order unreadable.
7. **Vendor authorization gate.** Connectors use **documented, official APIs only**. Never read a vendor's database directly, reverse-engineer an undocumented protocol, or encode a vendor's internal schema. Before a connector for a proprietary ERP is published, the maintainer must hold written confirmation from the vendor that publishing is allowed and which interface the connector may use. Ask the maintainer whether that confirmation exists. If the only access path is undocumented, stop and ask. Each connector change links the API's terms of use and notes whether publishing a client is allowed.
8. **Semantic versioning** from the first release. The canonical model and the connector interface are the public API. Changing a field is a breaking change. Record API changes in `CHANGELOG.md` with their semver impact.

## 4. Stack and conventions (defaults, the maintainer reviews)

- Java 21. Maven, three modules (section 1). Group id placeholder: `io.github.henriquevmdev`. Base package: `io.github.henriquevmdev.erpconnector`; connector modules live under `...erpconnector.connector.<erp>`.
- Code, identifiers, test names, README, javadoc and commit messages in **English**.
- HTTP: `java.net.http.HttpClient`. JSON: Jackson, only in connector modules.
- Tests: JUnit 5, AssertJ, WireMock for HTTP stubs, ArchUnit. Mockito only if really needed.
- Prefer immutable types (records) for the model. Money as `BigDecimal` plus currency, never `double`. Timestamps as `Instant` in UTC.
- CI (GitHub Actions): build, tests, ArchUnit rules, and a secret scan (gitleaks or equivalent).
- Publication later: GitHub Packages first, Maven Central if it makes sense.

### Build and test
- `mvn verify` from the root runs every module's tests, including ArchUnit. Use `mvn clean verify` after deleting sources (stale classes in `target/` are still scanned).
- Modules: `core`, `testkit`, `connector-fake` (in-memory connector for testing the testkit, not published).
- ArchUnit rules for connectors live in `testkit` (`ArchitectureRules`); `core` has its own copy in `core/src/test` because it cannot depend on `testkit`.
- CI: `.github/workflows/ci.yml` (build + gitleaks).

## 5. Architecture (draft: propose the final design and wait for approval)

### Canonical model
Starting point, to be refined from the questions that consumers of the data need answered (the maintainer will provide the initial list).

- **Order:** source ERP id, `externalId`, visible order number, the sales channel's own order number when given (e.g. the marketplace order number); `createdDate` (`LocalDate`), plus `createdAt` and `updatedAt` as optional `Instant`s, filled only when the ERP provides a time and zone (Bling and Tiny provide neither, see `docs/research/erp-comparison.md`); canonical status plus the ERP's original status text; **sales channel** (`DIRECT`, `MARKETPLACE`, `UNKNOWN`, plus the raw channel text); customer, items, payments; shipping, total discount, total, currency; optional invoice reference (NF-e access key); list of normalization anomalies.
- **Customer:** document type (CPF, CNPJ, other; absent when none), normalized value (no mask, upper case: CNPJ can be alphanumeric since July 2026), whether the check digits are valid; name; e-mail and phone if provided; city and state (UF) if provided, never the full address; birth date if provided (optional, may never exist). `toString()` shows the name and city/UF, masks the rest.
- **Item:** SKU, description, quantity, unit price, discount, total.
- **Payment:** method (canonical plus raw text), amount, installments, paid-at if any.
- Immutable types. "Not provided" is `Optional.empty()`, never null, zero or empty string. The raw ERP payload is **not** kept in the canonical object.

### Connector interface (implemented: `core.connector.ErpConnector`)
- `info()`: ERP id (the value of `Order.source()`) and capabilities (filter by update date, `updatedAt` in payload, webhooks, sandbox). Never calls the ERP.
- `checkConnection()`: returns normally, or throws `AuthenticationException` / another `ConnectorException`.
- `listOrders(changedFrom, changedTo)`: first page of the orders changed in `[changedFrom, changedTo)`, start inclusive, end exclusive. The caller passes `changedTo`, so the library never reads a clock.
- `listOrders(cursor)`: next page. The cursor is an opaque `String`, valid only for the connector's ERP account. An empty `nextCursor` ends the read.
- `fetchOrder(externalId)`: one order, or empty.
- Authentication: OAuth2 connectors will get a `TokenStore` implemented by the consumer, written together with the first OAuth connector.

### Sync semantics (proposal)
- At-least-once delivery. The same order can arrive more than once. The consumer deduplicates by (source, `externalId`). When `updatedAt` is present it picks the newest version; when absent, the last read wins.
- ERPs edit orders after creation, sometimes days later. Consumers should re-read an overlap window (the last N hours) on each sync. The library documents this and does not solve it alone.

### Error taxonomy (implemented: `core.error`)
`sealed` unchecked `ConnectorException` with `retryable()`: `AuthenticationException` (no retry), `RateLimitedException` (optional `retryAfter`), `TransientException` (timeouts, 5xx, deadlocks; retried), `PermanentException` (other 4xx, missing table or column; optional `httpStatus`, empty for non-HTTP connectors), `UnexpectedFormatException` (order id when known, and the field; never its value).

### Retry policy (implemented: `core.retry`)
`Retrier` repeats only retryable failures within a `RetryPolicy` (default: 3 attempts, waits from 1 s up to 30 s, exponential backoff with full jitter). A rate limit's `retryAfter` is obeyed exactly; if it is longer than the maximum wait, the failure is thrown at once. When the budget is spent, the last failure is thrown as is. No unbounded loops.

## 6. Testing

- The **conformance suite** in `testkit` is a base class every connector extends. At minimum it checks:
  - complete pagination, no order lost or duplicated within one read;
  - the incremental filter respects the given timestamp;
  - idempotency: reading twice gives the same result;
  - every error type is mapped (401/403, 429, 5xx, timeout, malformed response);
  - a missing field becomes unknown, never an invented value; unknown channel becomes `UNKNOWN`;
  - an invalid CPF/CNPJ produces an anomaly and does not abort the read;
  - no personal data or token appears in logs or exception messages.
- Validate the conformance suite first against a fake connector, to prove it fails when it should.
- Each connector has its own WireMock tests with synthetic fixtures based on the ERP's documentation.
- **Tests must fail when the code is wrong.** A test that only proves the code runs is not a test.
- ArchUnit rules: `core` does not depend on connectors, Spring or Jackson; no cyclic dependencies between modules.
- Contract tests against a real ERP test account are opt-in through an environment variable and run outside the default build.
